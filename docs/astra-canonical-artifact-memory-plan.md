# Astra Canonical Artifact Memory Plan

## Summary

Astra currently remembers work through prompt-time context rather than a dedicated memory store:

- the current thread goal, description, assistants, and session refs;
- recent `completedTasks` passed to the planner;
- teamwork `previousRounds` persisted in run diagnostics;
- plan task rows and task result summaries in the thread store;
- workspace artifact files under `.sessio/astra/<run-id>/tasks/`.

That is enough for short runs, but it does not give long-lived artifacts such as a plan, outline, research brief, or manuscript draft a stable identity. The planner can see paths, but it cannot reliably know which artifact is the current canonical outline or current plan.

This plan adds canonical artifact registration. It complements the [Astra Continuation Run Plan](./astra-continuation-run-plan.md): continuation runs should reuse current canonical artifacts when deciding where to continue.

## Current Problem

- Task artifacts are ordinary markdown files, not typed thread memory.
- Planner prompts include excerpts and paths, but older context can fall out of the short `completedTasks` window.
- The run journal is capped and summary-oriented, so it should not be the only source for current plan/outline state.
- Relying on task titles such as "plan" or "outline" is fragile.
- `sessio-work-state` is not the right dependency for planner memory. The backend can read thread work state directly from the store, and the planner should receive structured context from Sessio rather than having to call a skill or CLI to discover state.

## Current Artifact Generation

Astra task artifacts are generated by the Sessio backend, not by the assistant directly.

Current flow:

1. A delegated assistant returns a final task result as text.
2. Astra records the task result and plan task status.
3. The orchestrator converts each task completion's final output into a markdown artifact.
4. The markdown file is written under `.sessio/astra/<run-id>/tasks/<task-title>--<task-id>.md`.

Important limits:

- The current generic artifact write path runs for teamwork and brainstorm tasks. Process and debate do not use this shared artifact path today.
- Artifact writing is best-effort. A write failure is logged and skipped; it does not fail the Astra run.
- If the process stops after a task result is recorded but before the orchestrator writes artifacts, the thread may only have task status and result summary, not a markdown artifact file.
- Cancelled tasks should not be treated as having a valid output artifact.
- Files created directly by an assistant in the project workspace are not automatically Astra artifacts. They become canonical only if Sessio explicitly registers them or a later backend step writes/registers a Sessio artifact for them.

Canonical artifact memory must therefore register only paths that the backend has confirmed. If a task output exists only as final text, Sessio should first write a markdown artifact and then register that path. If no file can be written, the registry update should be skipped and a non-fatal diagnostic recorded.

## Canonical Registry

Add a persistent registry for thread-scoped Astra artifacts.

V1 scope is teamwork only. Brainstorm can keep using ordinary artifact paths in board context, but it should not promote participant outputs into thread-scoped canonical artifacts yet. If brainstorm canonical memory is added later, the registry key must gain a participant or board-lane scope so multiple participant drafts do not overwrite each other.

Proposed table: `thread_astra_artifacts`

Fields:

- `id`
- `thread_id`
- `astra_run_id`
- `source_task_id`
- `role`
- `title`
- `path`
- `summary`
- `is_current`
- `created_at`
- `updated_at`
- `superseded_at`

`source_task_id` stores the persisted plan task id, not the raw planner proposal id. Astra planner proposal ids are replaced when plan tasks are created, so registry provenance must use the stable `plan_task_id` for cross-run audit and continuation.

`role` is the stable semantic key. Store it as `TEXT`, not as a database enum, because artifact roles will evolve with workflow domains. The registry should prevent spelling drift through normalization and catalog validation, not by hard-coding the database to one fixed role list.

Normalize every incoming role before parsing, persistence, and lookup:

- trim leading and trailing whitespace;
- lowercase;
- convert internal whitespace and hyphens to underscores;
- reject empty roles and roles that do not match the normalized role slug format.

Initial built-in recommended roles:

- `plan`
- `outline`
- `research_brief`
- `draft`
- `synthesis`

Role compatibility rules:

- Store only normalized canonical role names, never planner-provided aliases.
- `artifactRole` and `usesArtifactRoles` both use the same normalize and alias resolution path.
- Keep a role alias map in code or config for compatible renames. For example, if `outline` later becomes `novel_outline`, old accepted planner output can be mapped deliberately rather than silently creating a new role.
- If a role is renamed, split, or merged, add a migration or explicit compatibility mapping so old threads continue to resolve their current artifacts.
- The built-in role list is used for planner guidance, compatibility checks, and diagnostics. It is not a DB enum and should not be the only source of accepted roles.
- User-authored or workflow-authored YAML may introduce custom roles, but custom roles should be explicit in the workflow or thread role catalog before they are accepted as canonical roles.
- Planner-generated roles that are neither built-in, aliased, deprecated, nor explicitly declared custom roles should produce a planner parse error or diagnostic instead of being inserted. This avoids typo roles such as `outlien` silently splitting the canonical artifact line.

Artifact role evolution rules:

- Treat the artifact role catalog as a versioned backend contract. Planner prompts expose only active canonical role names for the current version, including explicitly declared custom roles for the current workflow or thread.
- Parser and store reads may accept deprecated role names through the alias map, but planner context should emit the resolved canonical name so new plans converge on the current vocabulary.
- Store reads must tolerate historical roles that are no longer in the active recommendation list. They should remain queryable and should produce diagnostics only when they cannot be resolved through the current catalog or alias map.
- A pure rename is compatible through alias resolution plus an optional data migration that rewrites stored `role` values to the new canonical role.
- A role split is not automatically inferable. Keep the old role as deprecated and resolvable until a migration or a new task can deliberately promote the artifact into one of the new roles.
- A role merge must define a deterministic conflict rule for multiple current artifacts, such as newest successful current artifact wins, and preserve superseded rows for audit.
- Do not remove a deprecated role alias until all stored rows and continuation contexts that may reference it have a migration path.
- No separate per-row role schema version is required for v1 if migrations and aliases are tested, but adding one later is compatible because consumers should already resolve through the role catalog.

Rules:

- A thread can have many artifact versions per role.
- A thread has at most one current artifact per role.
- Registering a new current artifact for a role supersedes the previous current artifact.
- Superseded artifacts stay queryable for history and audit.
- Debate lanes remain isolated and do not automatically share canonical artifacts.

Database constraints and transaction rules:

- Add a partial unique index on current rows: `(thread_id, role) WHERE is_current = 1`.
- Add a role check constraint or equivalent parser validation for non-empty normalized role slug shape. Do not enforce the built-in role list as a DB enum.
- If role aliases are config-backed instead of hard-coded, the DB should still store canonical role names and planner context should expose only canonical names.
- Registering a new current artifact must happen in one transaction:
  1. set the old current row for `thread_id + role` to `is_current = 0` and `superseded_at = now`;
  2. insert the new current row with `is_current = 1`.
- If two same-role tasks complete concurrently, the transaction and unique index are the source of truth. The later successful transaction wins; the loser must retry registration against the refreshed current row or log a non-fatal diagnostic.
- `path` is workspace-relative and points at the immutable markdown task artifact. The registry does not rewrite task artifact files.

## Planner And Task Contract

Extend `AstraTaskProposal` with:

- `artifactRole: Option<String>`: the task is expected to create or update a canonical artifact with this role.
- `usesArtifactRoles: Vec<String>`: the task should read these current canonical artifacts before working.

Extend the teamwork orchestration YAML schema with the same fields. Both are optional for compatibility.

Allow workflow YAML to declare a role catalog when it needs domain-specific artifacts:

- `artifactRoleCatalog: Vec<String>`: normalized built-in or custom role names accepted for this workflow.
- The planner prompt should list built-in recommended roles plus workflow-declared roles.
- A task may use a custom `artifactRole` only if that role appears in the workflow or thread role catalog.
- This keeps role evolution cheap without letting accidental planner typos become persistent canonical keys.

Persist these fields whenever a task is converted into a plan task:

- Add `artifact_role TEXT` and `uses_artifact_roles_json TEXT NOT NULL DEFAULT '[]'` to `thread_plan_tasks`, or an equivalent side table keyed by plan task id.
- Include both fields in `AstraTaskProposal -> PlanTaskInfo -> AstraTaskProposal` round trips.
- This persistence is required for sequential rounds, deferred `dependsOn` waves, continuation runs, and task-completion artifact registration. In those paths the in-memory proposal may be reconstructed from `thread_plan_tasks`, so the artifact role fields cannot live only in the planner response object.
- This differs from `dependsOn`: `dependsOn` is in-memory wave scheduling metadata, while artifact roles are durable task semantics needed after task reconstruction and across continuation runs.
- Parser validation must normalize roles, resolve aliases, accept built-in roles and explicitly declared custom roles, and reject undeclared planner-only roles.

Planner prompt additions:

- Include `canonicalArtifacts` in the planner body.
- Each item includes `role`, `title`, `path`, `summary`, `sourceTaskId`, and `updatedAt`.
- Instruct the planner to read the referenced artifact path when the next decision depends on details beyond the summary.
- Instruct the planner to set `artifactRole` on tasks that update the current plan, outline, research brief, draft, or synthesis.
- Instruct the planner to set `usesArtifactRoles` when a task must build on a current artifact.

Implementation boundary:

- Add an `AstraPlannerContext` builder in the backend before calling `OrchestratorBackend::orchestrate`.
- The builder reads current canonical artifacts from the store and adds them to the planner prompt body.
- `build_astra_orchestration_prompt` should receive this context explicitly rather than querying the store directly.
- Runtime, deterministic, brainstorm, and debate backends should keep a consistent backend trait shape, even if only teamwork uses `canonicalArtifacts` in v1.
- Register canonical artifacts in the same orchestrator path that already writes task artifacts. Reuse the existing artifact writer and path helper instead of introducing another write location or path format.

Delegated task prompt additions:

- Inject the current artifact path and summary for each `usesArtifactRoles` entry.
- Keep the existing same-round dependency injection for `dependsOn`.
- If an artifact role is requested but no current artifact exists, state that explicitly so the agent does not assume hidden context.

## Artifact Update Flow

When a delegated task completes successfully:

1. Write the full output markdown artifact under `.sessio/astra/<run-id>/tasks/` using the existing `write_task_artifacts` flow.
2. Confirm the artifact path exists or the write succeeded.
3. If the task has `artifactRole`, register that output as the current artifact for the role.
4. Supersede the previous current artifact for the same `thread_id + role`.
5. Store a concise summary using a deterministic rule.

If artifact writing fails:

- Do not register a canonical artifact for that task.
- Keep the previous current artifact active.
- Record a non-fatal diagnostic so the planner does not receive a broken path.

Summary rule:

- Prefer the persisted plan task `result_summary` when it is non-empty.
- Otherwise use the task final output with any final-result marker stripped, then apply the existing `summarize_task_output` behavior.
- Truncate to a fixed prompt-safe limit, initially 600 characters.
- If both are empty, use `Astra delegated task completed.`.

When a task fails, errors, or is cancelled:

- Do not update the current artifact.
- Keep the previous current artifact active.
- Record the task result normally.
- Failed or errored tasks may still have ordinary diagnostic artifacts; they must not be promoted to current canonical artifacts.

## Test Plan

- Migration creates `thread_astra_artifacts`, task artifact role persistence columns or side table, indexes, constraints, and defaults.
- Parser accepts `artifactRole` and `usesArtifactRoles`, and remains compatible when they are absent.
- Parser normalizes artifact roles and accepts built-in roles, deprecated aliases, and explicitly declared custom roles.
- Parser rejects undeclared planner-only roles after alias resolution, while user-authored workflow catalogs can deliberately add custom roles without a database migration.
- Parser maps configured role aliases to canonical roles for both `artifactRole` and `usesArtifactRoles`.
- Store read tests confirm deprecated or historical roles remain queryable even when they are no longer recommended in planner prompts.
- Role migration tests confirm old canonical roles or aliases still resolve to the intended current artifact after a role rename.
- Plan task persistence round-trips `artifactRole` and `usesArtifactRoles` through sequential and reconstructed tasks.
- Registry stores multiple versions and keeps only one current artifact per `thread_id + role`.
- Registry current updates are transactional and protected by a partial unique index.
- Registry only points at backend-confirmed artifact paths; failed artifact writes do not produce current artifacts.
- Failed, errored, or cancelled tasks do not replace current artifacts.
- Registry provenance uses persisted `plan_task_id` as `source_task_id`.
- Brainstorm task artifacts are not promoted in v1.
- Planner prompt includes `canonicalArtifacts`.
- Planner prompt receives `canonicalArtifacts` through an explicit planner context builder.
- Delegated task prompt injects paths and summaries for `usesArtifactRoles`.
- Artifact summaries follow the deterministic priority and truncation rule.
- Continuation runs reuse current canonical artifacts when building planner context.

## Assumptions

- Canonical artifact memory is thread-scoped and run-aware.
- V1 does not add vector search or content indexing.
- The backend, not `sessio-work-state`, is responsible for supplying planner memory.
- `sessio-work-state` remains useful for stage/workflow agents that need to read or update stage state, but it is not a correctness dependency for Astra planner orchestration.
